# Title

Init task - configuration table

# Status

Accepted

# Context

We want to design a kernel which needs as less knowledge about applications that will run on the system as possible. 

Previous initialization system, inspired by [lk](https://github.com/littlekernel/lk/blob/master/app/inetsrv/inetsrv.c#L211), uses a section defined in the linker script and embedded in the kernel code to know what tasks to launch at startup.

Here we want less coupling between the application compilation process and the kernel one. One way to do that is to implement an initialization system similar to [linux](https://elixir.bootlin.com/linux/latest/source/init/main.c#L1518).

# Decision

We will use a **partition_table** which is compiled independently of the kernel code. Then this table is mapped in a predifined area in the binary file :

```C
           │               │
           │               │
           │       .       │
           │       .       │
           │       .       │
           │               │
           │               │
           │               │
           │               │
0x80100000 ├───────────────┤
           │               │
           │   part_table  │
           │               │
0x800FF000 ├───────────────┤
           │               │
           │               │
           │     kernel    │
           │               │
           │               │
0x80000000 └───────────────┘
```

The initialization code reads this section until it finds a **MAGIC_WORD** which identifes the end of the table. For each entry found, it creates the corresponding task. 

```C
           ┌───────────────┐      
           │               │      
           │               │      
           │      heap     │      
           │               │      
           │               │      
           ├───────────────┼      
           │               │      
           │  stack_part_1 │      
           │               │ ◄───┐
           ├───────────────┤     │
           │               │     │
           │       .       │     │
           │       .       │     │
           │       .       │     │
           │               │     │
0x80102000 ├───────────────┤     │
           │               │     │
           │     part_2    │     │
           │               │     │
0x80101000 ├───────────────┤     │
           │               │     │
           │     part_1    │     │
           │               │     │
0x80100000 ├───────────────┤     │
           │               │ ▲   │
           │   part_table  │ │   │
           │               │ ◄─┐ │
0x800FF000 ├───────────────┤   │ │
           │               │   │ │
           │    syscalls   │   │ │
           │               │   │ │
0x800FE000 ├───────────────┤   │ │
           │               │   │ │
           │               │ ──┘ │
           │     kernel    │ ────┘
           │               │      
           │               │      
0x80000000 └───────────────┘      
```

A stack for each task is dynamically allocated at this moment.

# Consequences

The biggest advantage of this method is to allow modification of the **partition_table** without kernel re-compilation. Also, thanks this added to dynamic allocation, the kernel needs no knowledge about the number of tasks that will run on the system. 

The partition table is statically defined, it would be nice to generate it through the build system.

It could also be nice to use a serialization format such as **CBOR** to write and read the configuration table.
